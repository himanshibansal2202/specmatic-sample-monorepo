## Background

In this sample project, we use Specmatic to contract test a Kotlin/Ktor BFF in isolation. Specmatic auto-generates REST contract tests from the BFF OpenAPI spec, starts dependency mocks from the backend OpenAPI and AsyncAPI specs, and verifies that the BFF preserves the contract boundary while calling those dependencies.

* [Product Search BFF OpenAPI spec](https://github.com/specmatic/specmatic-order-contracts/blob/main/io/specmatic/examples/store/openapi/product_search_bff_v6.yaml) is used for running contract tests against this BFF.
* [Order API OpenAPI spec](https://github.com/specmatic/specmatic-order-contracts/blob/main/io/specmatic/examples/store/openapi/api_order_v5.yaml) is used for stubbing the REST backend dependency.
* [Product audits AsyncAPI spec](https://github.com/specmatic/specmatic-order-contracts/blob/main/io/specmatic/examples/store/asyncapi/kafka.yaml) is used for mocking the Kafka dependency.

## Why Specmatic

* **Auto-generated tests from your API spec** - Specmatic reads OpenAPI and AsyncAPI specs and generates test cases automatically.
* **Intelligent service virtualisation** - dependency mocks come from the same contracts used for provider verification.
* **Backward compatibility detection** - contract changes can be checked before consumers and providers drift.
* **Works with existing OpenAPI and AsyncAPI specs** - no new DSL is needed for this sample.

## Run Contract Tests

### Prerequisites

Install Docker and set `SPECMATIC_LICENSE_KEY` in your shell. The test command uses the official Specmatic Enterprise Docker image `specmatic/enterprise:1.19.1`.

For **Unix based systems** and **Windows PowerShell**:

```shell
./scripts/test.sh
```

For **Windows Command Prompt**:

```shell
bash scripts/test.sh
```

First run may take 1-2 minutes as Specmatic clones the configured contract repository and Docker builds the app image. Subsequent runs are fast because contracts are cached in `.specmatic/` and Docker layers are reused.

The [specmatic.yaml](specmatic.yaml) file configures which contracts are tested and which dependency contracts are mocked.

#### View Specmatic Test Reports

After running the contract tests, you can view the HTML report generated by Specmatic in [build/reports/specmatic](build/reports/specmatic/). The same directory also contains the CTRF output for CI tooling.

### Test Modes

This sample ships with `schemaResiliencyTests: all` which runs the full test suite including negative and boundary tests. You can adjust the mode in `specmatic.yaml`:

| Mode | What it does |
|------|-------------|
| `none` | Runs tests from named examples only |
| `positiveOnly` | Adds all valid input combinations |
| `all` | Adds negative and boundary tests, expecting 400 for invalid inputs |

## How It Works

```text
BFF Spec -> specmatic.yaml -> Specmatic generates requests to the Ktor BFF -> the BFF calls Specmatic REST/Kafka dependency mocks -> Specmatic validates both sides
```

The test script builds the BFF Docker image, starts the app on a Docker network, then runs the Specmatic Enterprise Docker CLI on the same network. The app calls the REST mock at `http://specmatic:8090` and publishes product audit messages to the in-memory Kafka broker at `specmatic:9092`.

## Configuration

| Environment Variable | Default | Description |
|---------------------|---------|-------------|
| `SPECMATIC_LICENSE_KEY` | none | License key required by Specmatic Enterprise |
| `SPECMATIC_IMAGE` | `specmatic/enterprise:1.19.1` | Specmatic Enterprise Docker image |
| `SUT_BASE_URL` | `http://app:8080` | Base URL used by Specmatic tests inside Docker |
| `STUB_BASE_URL` | `http://localhost:8090` | REST dependency URL used by the Ktor app |
| `KAFKA_BROKER` | `localhost:9092` | Kafka broker used by the Ktor app |

## Project Structure

| File | Purpose |

| `scripts/test.sh` | Docker CLI test runner using Specmatic Enterprise |
| `Dockerfile` | Production container image that builds from source |
| `.github/workflows/ci.yml` | CI pipeline for test reports and Docker build |
